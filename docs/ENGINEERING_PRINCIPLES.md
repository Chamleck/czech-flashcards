# Принципи розробки та архітектури

Єдине джерело правил для коду й архітектури Czech Flashcards. Дивимось сюди **до** проєктування, **під час** написання нового коду й
**при** ревʼю старого. Кожне правило має ID; те, що можна перевірити механічно, перевіряє архітектурний гейт
(`scripts/check-architecture.ts`, команди — у розділі «Як це перевіряється»). Решту ловить чек-лист нижче (скіл `czech-flashcards-dev` вимагає його
пройти перед здачею).

Правила зібрані з рішень власника проєкту (Нік) у робочих чатах і звірені із загальною теорією проєктування: DRY / єдине джерело
істини, KISS / YAGNI, data-driven (table-driven) дизайн, відкритість до розширення без зміни рушія (OCP), чисте ядро без UI
(layered / hexagonal), «зроби неможливі стани нездійсненними» (make illegal states unrepresentable), fail-fast, архітектурні
fitness-функції (автоматичні тести архітектури) та «храповик» боргу (ratchet).

## A. Архітектура й код

| ID | Правило | Перевіряє |
|----|---------|-----------|
| **A1** | **Один факт — один дім.** Пул слів, перелік (роди, числа, відмінки), поріг, константа, хелпер — рівно в одному місці; решта імпортує. Дубль із однією зміненою деталлю — це опція спільного хелпера, а не друга копія. Спільне для 2+ квізів живе в `utils/quizCommon.ts` (загальне) чи `utils/partnerSelection.ts` (іменники, вокалізація). | `check:arch` A1 |
| **A2** | **Дані, а не код.** Знання — у даних слова (теги, поля); фрази — типізовані дані в `src/data/*Frames.ts`, не в рушії; жодних id слів чи лем у логіці; лексичний факт — типізоване поле. Поле описує, що ІСТИНА («слово парне»), а не яку дію виконати; один шматок коду перекладає факт у дію. Нове слово має потрапляти у фрази й квізи саме, без правок рушія. | `check:arch` A2 |
| **A3** | **Продовжуй, а не вклеюй.** Новий код іде за структурою, імпортами й іменуванням найближчого сусіда й розширює наявний механізм, а не будує паралельний. «У проєкті так заведено» кажемо лише після `grep` і ≥ 2 реальних входжень. Спільне виносимо на реальному повторенні, не наперед. | огляд, чек-лист |
| **A4** | **Легкість.** Без фантомних полів, мертвих експортів, абстракцій «на майбутнє». Моделюємо рівно потрібне. | `check:arch` A4 |
| **A5** | **Без милиць і крихкості.** Обмеження (тег, фільтр, skip) описує властивість слова чи фрази, а не відсіює конкретне слово. Ніщо не тримається на випадковому складі пулу (рід слів із тегом, кількість слів). Відомий ризик усувають, а не коментують. Fail-fast замість тихого запасного варіанту. Статичне рішення на етапі проєктування замість вимірювання на льоту; без повторних спроб замість структурного виправлення; без `any` / `@ts-ignore`; повторюваний поріг — іменована константа. | `check:arch` A5 (частково), `report:frames`, огляд |
| **A6** | **Правило там, де додають.** Кожен data-файл, що приймає слова, фрази чи теги, має шапку «ПРАВИЛА ДОДАВАННЯ». Нове поле чи тег іде з правилом у шапці й коментарем у типі. Зміна правила = обхід УСІХ коментарів, що описують механізм (header sweep). | `check:arch` A6; sweep — чек-лист |
| **A7** | **Типи як огорожа.** Рішення, без якого квіз стане хибним, — обовʼязкове поле (компілятор не збере без нього); закриті union; вичерпні `switch`; рішення, без якого квіз лише втратить питання, — необовʼязкове. | `tsc`, огляд |
| **A8** | **Шари.** `types` ← `data` ← `utils` ← `components` ← `screens`: залежності лише в один бік. `utils` і `data` — чиста логіка без React Native, щоб її можна було прогнати в Node (харнес, оракул). UI не містить мовних правил. | `check:arch` A8 |
| **A9** | **Повне покриття конструкцій.** Кожна клітинка існуючої форми питається. Виняток — лише `SkipRule` із причиною в даних (рушій і оракул читають те саме правило). «Повне» кажемо лише з виводу оракула. | оракул |
| **A10** | **Мова.** Чат — російська; коментарі, дані, UI — українська; чеські форми — чеські; жодного витоку російської в коментарі чи дані. | `check:arch` A10 |
| **A11** | **Один дім для рядків інтерфейсу.** Той самий текст у 3+ екранах — у `data/groupTitles.ts` чи спільному компоненті. | `check:arch` A11 |

## B. Процес (як перевіряти й здавати)

- **B1** Жодного коду без явної команди; питання й обговорення — не команда; на розвилці дизайну питаємо, а не вирішуємо мовчки.
- **B2** Перед здачею: `tsc` (0 помилок), архітектурний гейт (0 нових), оракул («Помилок: 0, відомих дірок: 0»),
  `--self-test` після змін оракула, гарнес на реальному рушії для змін квізів, silent-bug gate (пам'ять проєкту).
- **B3** Рефакторинг доводиться побітовим збігом на сідових прогонах старого й нового коду (+ мутація, що порівняння чутливе).
- **B4** Звіт про охоплення називає, що саме просканували («просканено N файлів, знайдено M») і чого перевірка НЕ бачить. Слова
  «дублювання немає» без такого охоплення — не звіт.
- **B5** Фраза з тегами проходить чек-лист (нижче) і звіт `report-frames`.
- **B6** Одна гілка — одна тема; нова тема — нова гілка; git: синхронізація, явні `git add`, один накопичувальний архів, `push`.

## Чек-лист для кожної нової фрази, тега, поля, хелпера (відповіді — в повідомленні про здачу)

1. Для кожного тега у вимогах фрази: яке слово він виключає і чим фраза неприродна саме для нього? Відповідь «ніяким» = милиця (A5).
   `report-frames --bank=ordinals` показує, що виключає кожен тег.
2. Фраза в називному множини не залежить від роду слова (теперішній час, прикметник на -í, «většina»)? Якщо присудок узгоджується —
   фраза тримається на випадковому складі пулу (A5).
3. Усі числові пороги — константи з імʼям і причиною? (A5)
4. Чи є вже такий пул / перелік / хелпер / константа в іншому файлі? Показати `grep`, а не казати «ні» (A1, B4).
5. Нове поле / тег / правило: шапка файлу, коментар типу, header sweep по всіх згадках механізму (A6).
6. Чи продовжує код сусіда (структура, імпорти, імена), і чи патерн підтверджено ≥ 2 входженнями (A3)?

## Як це перевіряється

Команди (у `package.json` скриптів для них немає; Claude запускає їх у своїй середі з кореня репозиторію):

```
npx tsc --noEmit -p tsconfig.json 2>&1 | grep -v TS5112
npx esbuild scripts/check-architecture.ts --bundle --platform=node --format=cjs --charset=utf8 --outfile=node_modules/.check-architecture.cjs && node node_modules/.check-architecture.cjs
npx esbuild scripts/check-quiz-coverage.ts --bundle --platform=node --format=cjs --charset=utf8 --outfile=node_modules/.check-quiz-coverage.cjs && node node_modules/.check-quiz-coverage.cjs
npx esbuild scripts/report-frames.ts --bundle --platform=node --format=cjs --charset=utf8 --outfile=node_modules/.report-frames.cjs && node node_modules/.report-frames.cjs --bank=ordinals
```

(оракул: додай `--self-test` або `--only=decl,nouns,…`; гейт: `--verbose` друкує відомий борг, `--update-baseline` лише за рішенням Ніка.)

Перевірку веде Claude у власному ізольованому середовищі, не ти. Дві команди чату:

- **«Перевір архітектуру»** — Claude бере свіжий `origin`, запускає `tsc` і архітектурний гейт, оракул (`--self-test` теж),
  `report-frames` по банках `ordinals` і `numerals`, а потім **вручну** проходить те, чого скрипти не бачать (A3, A5,
  A6-sweep, A7, природність фраз, сенс тегів), і звітує за ID правил: що перевірено, що просканено («N файлів, M знахідок»),
  чого перевірка НЕ бачить, що знайдено. Без такого звіту «перевірено» не кажемо (B4).
- **Автоматично перед кожною здачею** Claude проходить той самий список (B2) і додає відповіді чек-листа до повідомлення про здачу.

- Скрипт `scripts/check-architecture.ts` — «храповик»: нове порушення = помилка;
  відомий борг лежить у `scripts/architecture-baseline.json`, його видно в зведенні, але він не валить; борг лише скорочується
  (виправлений рядок скрипт просить прибрати; новий рядок — лише за рішенням Ніка).
- **Чого скрипти не бачать:** природність фраз, смисл тегів (чи описує тег фразу), вибір патерну сусіда, майже-копії (функція з
  однією зміненою деталлю), чи слово без тегу «безпечне». Це лишається за чек-листом і ручним проходом.
- Вимоги до самих скриптів: кожна нова перевірка перед додаванням доводиться мутацією (підкидаємо порушення — перевірка його
  ловить).

## Як змінювати правила

Нове правило = новий ID тут + (де можна) перевірка в `scripts/check-architecture.ts` з тим самим ID + рядок у чек-листі скіла.
Правило, що спрацьовує хибно, виправляємо в скрипті (і тоді перевіряємо саму перевірку), а не обходимо.
